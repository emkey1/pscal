# B0 baseline boards, local panel and frontier pair, 2026-10-07 to 2026-10-12

Plan item W1-19 (and the B1 / P0 requests that followed): measure the release that
ships today, before any guide or compiler change, on one frozen compiler.

This directory holds the boards run on local hardware plus B0-full on two cloud
models. It is not the whole baseline. The owner moved the bulk of the panel to
hosted inference part-way through; read it together with:

| directory | what |
|---|---|
| `../b0_devstral_mlx4bit_20261011/` | devstral-small-2 on its MLX 4-bit weights: B0, B1, P0 and the Python baseline, 3 repeats, complete |
| `../b0_openrouter_20261010/` | the same boards on hosted copies of four panel models (the baseline for future hosted boards); still running |
| `../b0_openrouter_free_20261010/` | a one-repeat survey of free hosted models |
| `../afm3_iphone18pro_20261011/` | Apple's on-device model on an iPhone 18 Pro, and the guide drafts tried on it |

Numbers below come from `summary.md` / `summary.json`, generated by
`summarize_b0.py --include-pending --weights panel_weights.json` from the unit
reports. `MANIFEST.json` pins every unit. `RUN_LOG.md` is the day-by-day record
of what happened, kept as written.

## What the failures say

- **Reading a file outside `fx`** (`FX-001` on `toon_parse_file`) is the most
  widespread first-attempt error among capable models: four model families on
  the panel boards, and on the free survey a 550B model whose only three misses
  are this.
  It is the single clearest medium-guide fix this baseline points at.
- **Silent-wrong** is the largest class for the mid-sized models (devstral 33 of
  78 first-attempt failures; Bonsai 8 of 18), mostly output-shape slips.
- **A compiler defect**, not a model error: `obj.field[lo..hi]` fails with
  `[SCOPE-001] identifier '__aether_slice_0' not in scope` on 2026-09-23-1,
  2026-10-06-1 and 2026-10-08-1. It cost first attempts in three model families.
  Write-up and reproducer in `findings/`.
- Between-repeat spread is small for the stronger models (Bonsai 0.0; hosted
  qwen models within 4 tasks of 73) and larger for the weakest. Plan 2.2 sizes
  B_G1's repeats from this; take it from the hosted twin, which has three
  repeats of every panel model.

## Incidents, and what they did to the data

Detail and timestamps are in `RUN_LOG.md`. None of these changed a scored case
that is in the tables; each either cost time or removed units.

1. Laptop sleep and a VPN outage on the first bench host produced
   infrastructure failures; the lanes moved to an always-on host. Aborted units
   are in `aborted_air/` and are not summarized.
2. The scheduler silently retried length-limited replies with 4x the budget;
   patched for this submitter, and the output cap was raised from 24,000 to
   96,000 tokens. The qwen3.5-9b unit finished under the old cap is in
   `B0/superseded_cap24k/` and is not summarized; it was re-run.
3. A harness update deployed while units were running mixed two harness
   versions; affected requests failed as infrastructure and were re-run.
4. qwen3.5-9b on the fast host produced 2.5-hour requests; the request deadline
   counts queue time and a timed-out request is not cancelled, so the queue
   stalled for 33 hours. Its local board was abandoned after one unit.
5. Four units asking for one model load at once were refused by the server; the
   driver now warms a model with one unit before opening the other slots.
6. prism-coder-7b's 32K window is shared between requests in flight; with four
   at once nearly every reply was "context size exceeded", returned by the
   scheduler as an empty success. Every unit from that window is in
   `aborted_m4mini/` and is not summarized; the model was re-run one request at
   a time.
7. The server resolved the devstral model name to a different weight file (MLX
   4-bit instead of the Q8_0 GGUF) after the host rejoined a shared pool. Units
   from that window were moved to the sibling directory and completed there as
   a separate, self-consistent set.

## Before the next board

- Pin the weight **file**, not the model name, and have the lane record the
  loaded file per unit. A model name with two downloaded variants changed
  underneath this run.
- Fix the scheduler path of the harness: count the request deadline from the
  start of generation, cancel the job when giving up, and treat a provider 5xx
  as a failure rather than an empty reply. Until then, one-slot hosts and
  long-running models do not mix.
- Check slots x prompt size against each model's window before fanning out.
- Do not deploy harness changes while units run (each request spawns a fresh
  worker that loads the new code under the old parent).
- Decide repeats per model up front: three where inference is cheap, one for
  small or slow local models, and label one-repeat rows.
- Record the interpreter and keep it out of a package manager's reach during a
  run (a Python upgrade removed the interpreter under a running board on the
  phone lane).
